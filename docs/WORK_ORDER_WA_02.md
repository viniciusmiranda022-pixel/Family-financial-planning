# Work Order — WA-02 LLM tool-driven orchestrator

Issue: #74
Parent: #71
Depends on: merged #73 / WA-01

## Objective
Implement the provider-decoupled natural-language orchestration layer defined by WA-00 and issue #74. The LLM understands and plans; Family Finance tools calculate, validate and return authoritative financial facts. No phrase catalog, SQL generation, raw ORM access, or direct LLM persistence.

## Scope
1. Introduce a provider-neutral LLM adapter contract compatible with the WA-00 ADR. Do not make personal ChatGPT/Codex OAuth a production multi-user dependency.
2. Define schema-validated structured planning/tool-call contracts and fail closed on malformed or unauthorized calls.
3. Implement a strict allowlist of generic semantic tools for entity resolution, periods, metrics, filters, grouping, comparisons and only actions already permitted by existing typed-action contracts. Tools must call existing domain/service layers; they must not expose SQL/raw ORM to the model.
4. Support multi-tool plans for compound questions without hard-coded sentence/intention catalogs or regex as the primary intent engine.
5. Resolve relative dates in America/Sao_Paulo and handle natural synonyms through the model/semantic layer rather than phrase-specific code.
6. Return needs_clarification whenever material account/card/owner/date/category/action information is missing or ambiguous. Never silently guess critical financial facts.
7. Add sanitized technical traces containing tool names, validated argument shapes/result metadata and decision state, but no unnecessary financial payload, secrets, phone plaintext or prompt content.
8. Add prompt-injection/tool-escape defenses: system boundary, strict tool allowlist, schema validation, no arbitrary tool names, no raw DB/file/network execution, bounded tool-call depth/count and safe failure.
9. Demonstrate with tests that materially equivalent formulations and at least several novel compound questions are answered by generic tool composition without code changes for each phrase.
10. Preserve household/user authorization server-side through every tool invocation.

## Financial invariants
- LLM never becomes a second financial engine. Numeric facts come from deterministic Family Finance services/tools.
- REALIZADO/COMPROMETIDO/PREVISTO remain distinct.
- Invoice payment is not a new expense; internal transfer is not income/expense; installments preserve contracted/monthly/future semantics; reversals neutralize without deleting history; partial payment carries principal and separates charges.
- Confirmed account/investment balance remains sovereign at the observed instant; no synthetic application/redemption or balancing transaction.
- Vinicius commission is not automatically PREVISTO; Kelly recurring salary follows existing documented mechanism only.

## Required tests
- Provider adapter contract and structured-output/schema rejection.
- Tool allowlist and injection/unknown-tool rejection.
- Household isolation and authorization propagation.
- Relative dates/timezone boundaries.
- needs_clarification for materially incomplete/ambiguous requests.
- Multiple paraphrases for the same semantic request without phrase-specific branches.
- Novel compound questions requiring multiple generic tools.
- Deterministic numeric parity with existing finance engine/services.
- Trace sanitization/PII-secret non-leakage.
- Regression suite, lint, CI and PostgreSQL jobs as applicable.

## Prohibitions
- No `if pergunta == ...`, closed phrase catalog, regex-driven primary intent router, SQL generated by the model, generic SQL/raw ORM tool, arbitrary code/file/network tool, direct LLM DB writes, second financial calculator, silent guessing, or WA-03+ transport mutation scope.
- No Oracle/OCI work.
- No paid recurring external LLM/API dependency without a documented Technical Challenge and evidence that the approved local/provider strategy cannot satisfy the requirement.
- Claude does not merge.

## Acceptance
WA-02 is acceptable only when a previously unseen compound natural-language question can be planned into allowed generic tools, validated by schemas, executed under the correct household/user authorization, and answered from deterministic Family Finance results without adding phrase-specific code; malformed/injected/ambiguous requests fail safely. Full CI must be green on a stable head SHA.
