# Work Order — WA-04 Generic Financial Analytics (#76)

## Objective
Implement the generic read/query layer for free-form financial questions. The LLM chooses and composes typed tools; Family Finance alone resolves periods, applies financial semantics, calculates and returns exact structured results.

## Scope
- Generic read tools, including justified equivalents of `financial_aggregate`, `search_transactions`, `compare_periods`, `get_income`, `get_expenses`, `get_balances`, `get_commitments`, and `get_installments`.
- Composable canonical filters: period, category, account/card, holder, transaction type, merchant/description and other existing dimensions.
- Grouping by month/category/account/card/holder and existing canonical dimensions.
- Backend metrics: total, average, count, min, max, percentage share, absolute variation and percentage variation.
- Deterministic relative-period resolution in `America/Sao_Paulo`.
- Multi-tool composition for compound questions using structured results only.
- Household isolation and existing RBAC on every read.

## Financial invariants
- Reuse existing canonical classification/status semantics; do not create a second financial engine.
- Operational income/expense excludes internal transfers, applications, redemptions, reconciliations and every other excluded/non-operational type defined by the October rebaseline and financial rules.
- Invoice payment is not a new expense. Confirmed balances remain sovereign at the observed instant. REALIZADO/COMPROMETIDO/PREVISTO must not be mixed.
- No hypothesis inferred by the LLM becomes a fact or filter silently; material ambiguity returns clarification.

## Acceptance criteria
- The minimum examples in issue #76 work through generic tools without phrase-specific code.
- Novel paraphrases and unseen combinations work without adding endpoints or handlers per wording.
- Exact backend results match canonical Family Finance calculations for equivalent deterministic queries.
- Compound comparisons are computed from structured backend results, never by asking the LLM to sum raw transactions.
- No cross-household leakage, raw-database dump, free SQL, or ORM/query expression generated by the LLM.

## Mandatory tests
- Fuel spend this month; grocery spend over last 3 months; income over last year.
- Top 5 categories by growth over 90 days; share of expenses for home/car/food.
- Equivalent paraphrases/unseen formulations with no code changes.
- Relative-period boundaries/timezone; zero denominators and percentage variation; empty periods.
- Exclusion semantics for transfers/application/redemption/reconciliation/invoice payment and status separation.
- Combined filters/groupings/metrics and multi-tool composition.
- Household/RBAC isolation and prompt-injection/tool-schema fail-closed behavior.
- Regression suite, lint, PostgreSQL integration where query semantics differ, migrations only if strictly necessary, and CI/GitHub Actions.

## Risks / review gates
Review query cardinality/performance, pagination/result limits, PII exposure, deterministic ordering, Decimal precision/rounding, category/account ownership, date boundaries, duplicate counting, installment semantics and compatibility with existing data.

## Prohibitions
- No static catalog of questions or phrase routing.
- No SQL generated by the LLM and no arbitrary SQL endpoint.
- Do not send the full database or unbounded transaction corpus to the model.
- Do not calculate/sum financial values in the LLM.
- Do not create a second financial engine or reinterpret canonical facts.
- Do not broaden into WA-05+ or Oracle/OCI (#59–65).
- Claude must not merge.
